The approver escalated (decision.md) over a race in `persistImapSyncWatermark` in `orchestrator/src/server/services/post-application/ingestion/imap-sync.ts` (around lines 318-354) and `updatePostApplicationIntegrationSyncState` in `orchestrator/src/server/repositories/post-application-integrations.ts` (around lines 171-202).

The save reads the integration, then writes `{ ...currentCredentials, syncWatermark }` back, and the update matches the row by id only. If the user disconnects (credentials set to null) or reconnects to the same host and username with a new password between the read and the write, the old credentials, including the encrypted password, are written back. Before this change the sync never wrote credentials.

Fix it so the watermark write can never resurrect old or removed credentials. Either do the read-compare-write in one synchronous better-sqlite3 transaction, or make the update conditional on the credentials (or `updatedAt`) that were read, and skip the write when the row no longer matches. Keep tenant scoping and the existing behaviour for the Gmail callers of `updatePostApplicationIntegrationSyncState`.

Add tests: (1) a disconnect that lands between the read and the write leaves credentials null and does not write the watermark; (2) a reconnect with a new password between read and write keeps the new password; (3) the normal path still saves the watermark. Also fix the reviewer's small note: do not log the new `lastUid` as stored when the save was skipped (log that it was skipped, without credentials). Re-run all seven CI-parity checks.
